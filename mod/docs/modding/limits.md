# Limits and budgets

Hard limits of the game's formats, and the memory budgets a mod must respect. The build checks what it can: a limit
that is exceeded fails the build (`budget <name>: N B > limit`) and nothing is written; softer figures come as warnings
and are listed in the build report. The figures come from the game's executable ([models.md](../models.md),
[hd-textures.md](../hd-textures.md)) and from measurements made in RPCS3; the engine code is the same in the native
port, but the video-memory figures have not yet been re-measured in the native port, and no mod has been run in the
game yet ([operations.md](operations.md)).

## Meshes

| limit | value | why |
|---|---|---|
| vertices per mesh | 32,767 | 16-bit strip indices; `0x7FFF` is the restart marker. The importer splits above 32,000 |
| indices per mesh | 65,535 | strip indices, including restarts and stitching |
| largest mesh in the stock game | 4,030 vertices (static), 10,797 (skinned) | for scale |
| UV values | within 0..1 where you can | stored as half floats: the resolution falls as the value grows. The importer range-checks them and shifts whole UV islands by integers where needed |
| LOD | none per mesh | zones swap whole to `_lod` paks; props and characters have one mesh set |

A mesh is one draw call with one material: a glTF primitive becomes one game mesh. Static imports split a primitive that
is over the limits automatically and say so; skinned imports split a mesh that is over the SPU budget (below). The
triangle lists you give are turned into strips by the kit.

## Skinned meshes

| limit | value |
|---|---|
| bone weights per vertex | 3: more are pruned to the 3 largest and renormalised; weights below `min_weight` (0.001) are dropped |
| bones | the human skeleton has 101, the board 9. Bone indices are bytes; the SPU budget is reported for 101 bones and for a 128-bone worst case |
| SPU skinning job | 99,999 bytes per mesh |

The SPU job holds the mesh's skin records (32 bytes per vertex plus a small header per group of vertices that share a
bone set), the skinned output (24 bytes per vertex) and the bone matrices (64 bytes per bone). With the 101-bone
skeleton a mesh stays on the SPU path up to roughly 1,600 vertices; the build computes the exact size of every
mesh ("max SPU job 83,552 B") and splits a changed mesh until each part fits. A mesh over the budget is still valid:
the game then skins it on the CPU (the PPU), which is slower. 11 stock skins already do (a 2,302-vertex secret skater,
some CAS trousers, some boards). `allow_ppu` keeps a big mesh in one piece.

A custom CAS skater costs no extra video memory over Tony Hawk: the skater slots are fixed.

## Textures

| limit | value |
|---|---|
| formats | DXT1, DXT1 with 1-bit alpha, DXT5, 32-bit (the normal-map kind DXT5nm exists in the game; a new material gets the glTF's normal map, or a flat one) |
| size | a power of two, up to 2048 px: any other size is resized to the nearest power of two. Textures the skin operations create from your picture are capped at 1024 px |
| mips | generated by the kit for dictionary textures (single `.img` images, such as deck graphics, have one level) |
| not supported | cube maps, volume textures |
| format on replace | the entry's own format is kept; a picture with alpha turns DXT1 into DXT5 (or punch-through DXT1 for a 1-bit alpha) |

A texture's pixels live in the paired vram file, so a bigger texture grows the vram pak of its zone or skater. A skater's
textures are shared and small (128-512 px), and a deck graphic is 128 x 256 in the stock game.

## Zone video memory

All the zones share **four fixed video-memory link slots**, and every slot is as big as the **largest zone `_vram`
pak** of any zone (the game measures the files on the disc when a level loads), rounded up to 0x800. So the budget is
global:

```
free video memory (stock memory) = 58.86 MiB - 4 x (slot - stock slot)        stock slot = 14,786,560 B
```

- `Z_Houses` is the largest zone in the stock game: its `_vram` pak is 14.10 MiB (14,786,176 bytes, a slot of
  14,786,560). Every byte you add to `z_houses_vram` costs four bytes of free video memory, because all four slots
  grow. The ramp example grows it by 65,920 bytes (to 14,852,096): 0.25 MiB of VRAM in total, free memory 58.61 MiB.
- Other zones have headroom up to the slot: adding to them costs nothing until they exceed it.
- The build fails when the predicted free memory would drop below 8 MiB (the reserve) and warns whenever
  the largest zone grows; the report records `zone_vram_slot`, `zone_vram:<zone>` and the predicted free memory.
- HD texture packs raise the largest zone (cap22: 21.95 MiB, full: 31.21 MiB), and with it the size every zone may
  reach for free. The build starts from the files the overlay serves below the mod pack, so it sees such a pack.
- The allocator has no failure path: running out shows as corruption or a crash, not as an error message.

Header paks (main memory) are checked against the largest stock zone header pak (3,302,272 B, `Z_Ghetto`); a bigger one
is a warning, because the heap limit behind it is not verified (`zone_header:<zone>`). The Houses header pak after the
ramp example is 1,890,688 B.

Other users of video memory: LOD paks (about 5 MiB), CAS `cas_shared` 22.8 MiB plus one CAS type 11.5-15.1 MiB, the global
pak 4,500K, the pedestrian parts 24,500K (386 KB slack), mission paks 4,600K, the shop and cutscene pak 4,400K, the
loading screen 800K, the sky 600K.

## Heaps (main memory and video memory outside the zone slots)

These areas have a fixed size set by the game's scripts. The build checks them (the budget names are in the build
report):

| heap | main memory | video memory | check |
|---|---|---|---|
| global pak (`global.pak` + `.pab`, `global_vram.pak`) | 1,843,200 B (spare ~53 KB) | 4,608,000 B | `heap_global_pak.main` / `.vram`, fails over the size |
| pedestrian parts (`z_peds`) | 6,656,000 B (spare ~211 KB) | 25,088,000 B (spare ~395 KB) | `PedParts.main` / `.vram`, fails over the size |
| placed people (`peds.add`) | | | `peds.placed:<zone>`: fails over 22 per zone (the most the stock game creates at once), warns over 12; the models must be resident in `z_peds` ([peds.md](peds.md#limits)) |
| skater geometry (`skatergeomheap`, one per skater) | 614,400 B (spare ~350 KB) | 3 MiB (spare ~1.7 MB) | `skatergeomheap.main` / `.vram (<appearance>)`: an estimate of the appearance's parts + board + the rest; fails over the size |
| mission pak | spare ~132 KB | | `mission_pak:<file>`: fails over the stock size + 132,000 B |
| `cas_shared`, `cas_<type>` paks | no fixed heap | no fixed heap | `pak.<name>.main` / `.vram`; a warning if the pak grew by more than 2 MiB main / 8 MiB video: the free-skate main-memory gap is about 11 MiB and the frontend holds all CAS paks at once |

The Tony Hawk example uses 306,000 of 614,400 B (main) and 1,467,390 of 3,145,728 B (video) of the skater geometry
heap. Each zone also has scene and model budgets in the game's scripts (about 8.6 MB scene, 286 KB model); how the
engine enforces them is not known, so stay well below the size of the largest stock zone.

## Collision and nodes

Per operation: 65,535 triangles, 65,535 vertices, 254 distinct material words ([collision-rails.md](collision-rails.md)).
There is no measured budget for the size of a zone's collision file or its number of bodies (the build reports the
`.hkc` size, 540,304 B after the ramp example); keep it simple. Rails: at least two points, no segment shorter than
5 cm.

Grind rails live in `global_rails.pak`, loaded into a fixed RailNodeHeap (stock 1,761,280 B against a stock pak of
1,742,848 B: room for about 150 new rail points). `rails.add` raises the heap in the game's start-up script in 64 KiB
steps when a build needs more (verified in game with 240 extra points); the build report records
`RailNodeHeap (global_rails.pak)`.

## Zones: other things to know

- An added object is in the full zone only: not in its `_lod` stand-in, so it is invisible from a neighbouring zone's
  distance view.
- Static geometry is stored in world space; it is drawn only when its material has a shader block, which new objects
  get from a material the game already has (the kit clones one).
- Collision is separate from the mesh ([formats.md](formats.md)): an added object without a collision operation is
  visual only.
